# 7 天 7 夜：我和 5 个 AI 助理的 Coding 实验

> 这是一次技术实验，不是真正的创业项目。我们想验证：当 AI 足够强大时，一个普通人能否独立完成一个完整的产品开发？

---

## 第一章：缘起——为什么做这个 AI 社交产品

凌晨两点，我盯着电脑屏幕发呆。

这已经是我第 N 次思考一个问题：**如果 AI 已经能写代码、能做设计、能写文档，那一个不懂技术的产品经理，能否独立完成一个完整的产品开发？**

不是那种"用 AI 辅助写几行代码"的浅尝辄止，而是真正的**全流程 AI 驱动**——从产品构思到代码实现，从部署上线到运维监控，全部交给 AI 团队。

于是，AI-Pick 这个项目诞生了。

### 实验目标

这不是一个要真正上线运营的产品，而是一次**技术验证**：

1. **验证 AI Coding 的能力边界** —— AI 能否理解复杂业务逻辑？
2. **验证多 Agent 协作的可行性** —— 多个 AI 能否像真人团队一样配合？
3. **验证开发效率的提升幅度** —— 传统开发需要多久？AI 开发需要多久？

我们给自己定了一个看似不可能的目标：**一周内，完成一个 AI 社交小程序的从 0 到 1。**

### 产品定位

AI-Pick 是一款 AI 驱动的兴趣 + 熟人社交小程序，核心解决一个痛点：**想找人玩，但找不到同好。**

### 核心功能

产品包含四个核心模块：

**🤝 搭子模块**
- 基于兴趣匹配（游戏、运动、学习、美食）
- 支持发布搭子需求和应征
- AI 智能推荐匹配度高的搭子

**🎉 活动模块**
- LBS 附近活动发现
- 活动创建和报名
- 活动签到和回顾

**👥 同事圈/校友圈**
- 公司认证（邀请码机制）
- 学校认证（邀请码机制）
- 熟人社交网络

**🏠 AI 首页**
- 对话式发现引擎
- 自然语言搜索（"帮我找北京周末的羽毛球活动"）
- 智能推荐 feed 流

### 技术选型

基于实验目标，我们选择了成熟的技术栈：

- **前端**：微信小程序（覆盖最广的用户群）
- **后端**：Spring Boot 3.2 + MyBatis-Plus（Java 技术栈最成熟）
- **数据库**：MySQL 8.0 + Redis（经典组合）
- **AI 能力**：阿里云百炼（qwen3.5-plus 模型）
- **部署**：阿里云 ECS + Docker 容器化

技术选型的核心原则：**成熟、稳定、AI 熟悉**。这不是尝试新技术的实验，而是验证 AI 开发流程的实验。

## 第二章：团队组建——我的 5 个 AI 员工

传统创业，你需要组建一个团队：产品经理、后端开发、前端开发、测试工程师、运维工程师。

而我，只用了**5 个 AI Agent**。

### Agent 团队架构

我给每个 Agent 分配了明确的角色和职责：

| Agent | 角色 | 职责 |
|-------|------|------|
| **pm-agent** | 产品经理 | 需求分析、产品设计、文档输出 |
| **backend-agent** | 后端开发 | Spring Boot 后端开发、API 设计、数据库设计 |
| **frontend-agent** | 前端开发 | 微信小程序开发、UI 实现、交互逻辑 |
| **test-agent** | 测试工程师 | 测试用例编写、自动化测试、质量保障 |
| **review-agent** | 代码审查 | 代码审查、提出改进建议、确保代码质量 |

### 我的角色：项目协调者

我的工作内容发生了根本性变化：

**不再是**：
- ❌ 写代码
- ❌ 调 bug
- ❌ 画原型
- ❌ 写文档

**而是**：
- ✅ 分配任务给对应的 Agent
- ✅ 检查各 Agent 的工作状态
- ✅ 协调各方确保项目按计划推进
- ✅ 把握产品方向和质量标准

简单来说：**我负责决策，AI 负责执行。**

### 任务分配流程

整个开发流程是这样的：

```
我（main agent）
  ↓ 分配任务（自然语言描述）
frontend-agent / backend-agent（活跃会话）
  ↓ 调用 cursor-agent skill
Cursor CLI → 代码修改
```

举个例子，当我需要开发一个 API 接口时：

1. 我对 backend-agent 说："创建一个搭子列表接口，支持分页和筛选"
2. backend-agent 调用 Cursor CLI，生成 Controller、Service、Mapper 代码
3. review-agent 审查代码，提出改进建议
4. backend-agent 根据建议修改
5. test-agent 编写测试用例
6. 我验收通过后，任务完成

### 踩过的坑：Agent 管理三原则

实验过程中，我踩了不少坑，最终总结出三条铁律：

**坑 1：一开始自己写代码，违背了 Agent 分工原则**

实验初期，我习惯了亲力亲为。有个紧急的 bug，我直接调用 Cursor 修复了。

结果：后续类似任务，我又自己做了。Agent 们 confused 了："这个任务到底是谁的？"

**解决**：明确规则，写入 MEMORY.md——**我（main agent）绝不直接写代码**，只负责协调分配。

**坑 2：每次分配任务都创建新会话，管理后台一堆重复 Agent**

一开始，我每次分配任务都 `sessions_spawn` 一个新的 backend-agent。

结果：管理后台出现了 10 个 backend-agent 会话，资源浪费严重，任务上下文还不连贯。

**解决**：会话复用机制——分配任务前，先检查目标 agent 是否有活跃会话。有则复用（`sessions_send`），无则创建（`sessions_spawn`）。

**坑 3：Agent 忘记之前定的规则**

今天说"用 RESTful 风格"，明天 Agent 生成的接口又是 RPC 风格。问就是"忘了"。

**解决**：重要规则必须写入文件（MEMORY.md、AGENTS.md），每次会话开始自动读取。**口头交代的规则不如有一个文件可靠。**

### 最佳实践总结

基于这些坑，我总结了 AI 团队管理的最佳实践：

1. **重要规则必须写入文件** —— 不要口头交代，写进 AGENTS.md
2. **复杂任务拆成小步骤** —— 每步有明确验收标准
3. **设定检查点** —— 避免跑偏，及时纠偏
4. **发现错误立即纠正** —— 让 Agent 记录到 LEARNINGS.md，避免再犯

## 第三章：开发实战——AI 是怎么写代码的

这一章，我们深入 AI 开发的黑盒，看看代码是怎么生成的。

### Cursor CLI：AI 的"手"

Cursor 是一个 AI 代码编辑器，我们的 Agent 通过 Cursor CLI 执行代码修改。

**工作流程**：

1. Agent 理解任务需求
2. Agent 调用 cursor-agent skill
3. Cursor CLI 在项目目录执行
4. Cursor 读取项目上下文（AGENTS.md、代码结构）
5. Cursor 生成/修改代码
6. Agent 验收结果

整个过程，我只需要说："创建一个搭子列表接口，支持分页和筛选"，剩下的交给 AI。

### 后端开发：20 个 API 接口

backend-agent 在一周内完成了 20 个 API 接口的开发：

- **搭子模块**（8 个接口）
  - 发布搭子、搭子列表、搭子详情
  - 应征搭子、应征者列表、接受/拒绝应征
  - 我的搭子、搭子状态更新

- **活动模块**（7 个接口）
  - 创建活动、活动列表、活动详情
  - 活动报名、报名列表、活动签到
  - 活动回顾

- **消息模块**（4 个接口）
  - 发送消息、消息列表、消息详情
  - 未读消息计数

- **首页推荐**（1 个接口）
  - 智能推荐 feed 流

每个接口的开发流程：
1. 定义 DTO 和 VO（数据传输对象）
2. 创建 Entity（数据库实体）
3. 编写 Mapper（数据访问层）
4. 实现 Service（业务逻辑层）
5. 编写 Controller（API 接口层）
6. review-agent 审查
7. test-agent 编写测试

**平均每个接口开发时间**：约 30-60 分钟（包括审查和测试）

### 前端开发：6 个核心页面

frontend-agent 完成了 6 个核心页面的开发：

1. **首页** —— AI 对话 + 推荐 feed 流
2. **搭子页** —— 搭子列表和详情
3. **活动页** —— 活动列表和详情
4. **消息页** —— 消息列表和聊天
5. **个人页** —— 用户信息和设置
6. **认证页** —— 公司/学校认证

微信小程序的开发流程：
1. 设计页面结构（WXML）
2. 编写样式（WXSS）
3. 实现交互逻辑（JS）
4. 配置页面路由（app.json）
5. 对接后端 API
6. review-agent 审查
7. 真机测试

### 踩过的坑：AI 开发的"暗礁"

**坑 1：Agent 不理解项目上下文**

初期，backend-agent 生成的代码经常不符合项目规范。比如：
- 包名不统一
- 命名风格不一致
- 缺少必要的注释

**原因**：Cursor 不知道项目的开发规范。

**解决**：在项目根目录创建 AGENTS.md，明确开发规范。Cursor 会自动读取这个文件。

```markdown
# AGENTS.md - 开发规范

- 包名：com.aipick.{module}
- 命名：驼峰命名法
- 注释：公共方法必须有 JavaDoc
- 异常：统一用 BusinessException
```

**效果**：后续生成的代码质量明显提升。

**坑 2：复杂逻辑需要多次迭代**

AI 不是万能的。复杂业务逻辑（比如匹配度算法）一次生成的代码往往有 bug。

**错误做法**：让 AI"重新生成一个完整的"
**正确做法**：拆成小步骤，每步验证

比如匹配度算法，我们拆成：
1. 定义匹配度计算接口
2. 实现兴趣标签匹配逻辑
3. 实现地理位置匹配逻辑
4. 实现时间匹配逻辑
5. 综合计算最终匹配度
6. 单元测试验证

每步都验证通过，再进入下一步。

**坑 3：调试过程有时比写代码还长**

有个接口一直返回 500 错误，AI 写了 3 版代码都没解决。

最后发现是数据库字段名拼写错误（`create_time` 写成 `createTime`）。

**教训**：
- 完整复制错误信息给 AI，不要自己概括
- 让 AI 参与调试，不只是写代码
- 有时候人类花 5 分钟能看懂的错误，AI 可能要调试很久

### 最佳实践

基于实战经验，总结以下最佳实践：

1. **项目根目录放 AGENTS.md** —— Cursor 自动读取，理解项目规范
2. **复杂修改先让 Agent 复述方案** —— 确认理解正确再执行
3. **每完成一个模块就测试** —— 不要全部做完再测
4. **错误信息完整复制给 Agent** —— 避免 AI 猜

## 第四章：AI 能力集成——让产品真正智能

AI-Pick 的核心竞争力是 AI 能力。这一章，我们看看 AI 能力是怎么集成的。

### 阿里云百炼 API 对接

我们使用阿里云百炼的 qwen3.5-plus 模型，提供以下 AI 能力：

1. **智能推荐** —— 基于用户画像推荐搭子和活动
2. **匹配度计算** —— 计算两个用户的匹配度
3. **AI 文案生成** —— 生成搭子描述、活动介绍
4. **自然语言搜索** —— 理解用户搜索意图

### Spring AI Alibaba 集成

使用 Spring AI Alibaba 框架，简化 AI 能力调用：

```java
// 伪代码示例
@Service
public class AiRecommendService {
    @Autowired
    private BailianClient bailianClient;
    
    public List<Partner> recommend(User user) {
        // 调用百炼 API，生成推荐结果
        String prompt = buildRecommendPrompt(user);
        String response = bailianClient.call(prompt);
        return parseRecommendation(response);
    }
}
```

### 核心 AI 功能实现

**1. 智能推荐算法**

推荐逻辑：
1. 获取用户画像（兴趣、位置、时间偏好）
2. 召回候选集（附近的人、相似兴趣的人）
3. AI 排序（百炼模型打分）
4. 返回 Top N 推荐

**踩坑**：初期推荐结果单一，总是推荐相同类型的内容。

**解决**：
- 增加随机因子（10% 概率推荐不同类型）
- 引入多样性指标（推荐结果覆盖多个兴趣标签）
- 记录用户反馈（跳过/聊聊），持续优化

**2. 匹配度计算**

匹配度算法：
1. 兴趣标签匹配（40% 权重）
2. 地理位置匹配（30% 权重）
3. 时间偏好匹配（20% 权重）
4. AI 综合评分（10% 权重）

**踩坑**：初期匹配度算法不准，匹配度 90% 的人完全不合。

**解决**：
- 调整权重（增加兴趣标签权重）
- 增加用户反馈机制（用户标记"不合"，降低类似推荐）
- A/B 测试不同权重组合

**3. 自然语言搜索**

用户输入："帮我找北京周末的羽毛球活动"

AI 理解：
- 地点：北京
- 时间：周末
- 类型：羽毛球
- 意图：找活动

然后转换成数据库查询条件，返回结果。

### 最佳实践

1. **API Key 用环境变量** —— 不要硬编码在代码里
2. **AI 结果加人工审核** —— 关键决策不要完全交给 AI
3. **记录用户反馈，持续优化** —— AI 模型需要数据喂养

### AI 如何高效完成部署

这是整个实验中最让我惊喜的部分：**AI 不仅能写代码，还能高效完成云端部署。**

**1. AI 设计部署方案**

- Docker 安装脚本
- MySQL 初始化脚本

- 健康检查脚本

### AI 部署的优势

这次实验让我深刻体会到 AI 在部署方面的优势：

**✅ 方案自动生成** —— 不需要查文档、不需要问同事，AI 直接生成完整方案

**✅ 脚本一键执行** —— 部署脚本 AI 写好，我审核通过后一键执行

**✅ 错误自动排查** —— 部署失败时，AI 分析错误日志，给出修复建议

**✅ 文档同步生成** —— 部署过程中，AI 同步生成运维文档

### 最佳实践

1. **用 Docker Compose 管理容器** —— 一键启停所有服务
2. **部署脚本自动化** —— 减少人工操作，降低出错概率
3. **健康检查接口必备** —— 快速判断服务状态

## 第七章：经验总结——AI 开发的得与失

实验结束，让我们客观评价 AI 开发的得与失。

### AI 开发的优势

**✅ 开发速度快**

传统开发一个完整的小程序（前后端 + 部署），至少需要：
- 产品经理：1 周
- 后端开发：2 周
- 前端开发：2 周
- 测试工程师：1 周
- 运维工程师：3 天

**总计**：约 6-7 周（按并行计算也要 3-4 周）

AI 开发：
- **总计**：约 20 几个小时（有效工作时间）

**效率提升**：约 10 倍

**✅ 代码质量稳定**

有 review-agent 把关，代码风格统一，注释完整，符合规范。

**✅ 24 小时工作**

Agent 们不需要休息。我睡觉时，它们在工作；我吃饭时，它们也在工作。心跳检查机制确保每半小时检查一次任务状态。

**✅ 学习成本低**

不需要学习 Java、Spring Boot、微信小程序开发。我只需要用自然语言描述需求，AI 负责实现。

### AI 开发的局限

**❌ 复杂逻辑需要多次迭代**

简单 CRUD 接口，AI 一次生成就能用。复杂业务逻辑（比如匹配度算法），需要多次迭代。

**❌ 需要人类把关方向**

AI 不会主动思考"这个功能是否必要"、"这个设计是否合理"。人类必须把握产品方向。

**❌ 规则容易忘记**

今天说的规则，明天 AI 可能就忘了。必须写入文件，每次会话自动读取。

**❌ 调试过程有时较长**

有些 bug，人类一眼就能看出来，AI 可能要调试很久。

### 哪些任务适合 AI

基于这次实验，我认为以下任务适合交给 AI：

- ✅ CRUD 接口开发
- ✅ 页面布局实现
- ✅ 单元测试生成
- ✅ 文档编写
- ✅ 部署脚本编写
- ✅ 代码审查

### 哪些任务需要人类

以下任务，目前还需要人类主导：

- ✅ 产品方向决策
- ✅ 复杂业务逻辑设计
- ✅ 性能优化
- ✅ 安全问题处理
- ✅ 用户体验把控
- ✅ 跨团队协调

### 给开发者的建议

如果你也想尝试 AI 开发，我的建议是：

**1. 把 AI 当同事，不是工具**

工具是被动执行的，同事是主动思考的。给 AI 明确的角色和职责，它会给你惊喜。

**2. 明确规则，写入文件**

不要口头交代规则，写进 AGENTS.md。AI 的记忆是文件，不是大脑。

**3. 设定检查点，及时纠偏**

复杂任务拆成多个检查点，每完成一步就验收，避免最后发现方向错了。

**4. 让 AI 记录错误，避免重复踩坑**

发现错误，让 AI 记录到 LEARNINGS.md。下次遇到类似问题，AI 会避免再犯。

**5. 人类负责方向，AI 负责执行**

这是最重要的原则。人类把握产品方向和质量标准，AI 负责具体实现。
