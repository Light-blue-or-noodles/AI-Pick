## 第一章：一个社恐的社交产品实验

说出来你可能不信，我做这个社交产品，是因为我**社恐**。

真的。每次想找人玩，打开微信翻了一圈，发现不知道该找谁。想找同好吧，朋友圈里没几个人感兴趣。想参加活动吧，又怕去了尴尬。

于是我想：**能不能有个 AI 助手，帮我搞定这一切？**

### 实验目标：验证 AI 能不能独立开发

当然，上面那个只是产品层面的想法。技术层面，我有一个更大的野心：

**如果 AI 已经能写代码、能做设计、能写文档，那一个普通人能否独立完成一个完整的产品开发？**

不是"用 AI 辅助写几行代码"那种过家家，而是真正的**全流程 AI 驱动**：
- 产品设计 → AI
- 代码开发 → AI
- 测试部署 → AI
- 运维监控 → AI

我负责什么？负责**提需求**和**验收**。

听起来很美好对吧？来，让我们看看现实。

### 产品定位：AI 驱动的社交小程序

产品名称：AI-Pick（中文名还没想好，反正也是实验项目）

解决什么问题？**想找人玩，但找不到同好。**

怎么解决？**AI 帮你匹配。**

## 第二章：我的 5 个 AI 员工，一个比一个能卷

传统创业，你需要：
- 产品经理 1 名（月薪 20k）
- 后端开发 2 名（月薪 30k × 2）
- 前端开发 1 名（月薪 25k）
- 测试工程师 1 名（月薪 20k）
- 运维工程师 0.5 名（月薪 25k × 0.5）

**总计**：约 120k/月（还不算社保公积金）

而我，只用了**5 个 AI Agent**。

**成本**：电费 + API 调用费（大概几百块？）

### Agent 团队架构

我给每个 Agent 分配了明确的角色：

| Agent | 角色 | 职责 | 特点 |
|-------|------|------|------|
| **pm-agent** | 产品经理 | 需求分析、产品设计、文档输出 | 话最多，最爱画饼 |
| **backend-agent** | 后端开发 | Spring Boot 后端开发 | 沉默寡言，代码狂魔 |
| **frontend-agent** | 前端开发 | 微信小程序开发 | 审美在线，细节控 |
| **test-agent** | 测试工程师 | 测试用例、质量保障 | 挑刺专家，专找 bug |
| **review-agent** | 代码审查 | 代码审查、提建议 | 毒舌，但说的都对 |

### 我的日常工作

以前我上班：
- 9:00 到公司，打开电脑
- 9:30 开始写代码
- 12:00 吃饭
- 13:30 继续写代码
- 18:00 下班
- 20:00 加班（自愿的）

现在我做这个项目：
- 想起来时，对 Agent 说："做个 XX 功能"
- Agent 开始工作
- 我去喝咖啡
- 回来验收
- 通过 → 下一个任务
- 不通过 → "改一下"

**工作时长**：每天有效工作约 1-2 小时
**工作强度**：主要是动嘴，不动手

### 踩过的坑：Agent 管理血泪史

听起来很美好？来，看看我踩的坑。

**坑 1：我忍不住自己写代码**

实验初期，有个紧急 bug。我想着"算了，我自己修一下更快"，直接调用 Cursor 修复了。

结果：后续类似任务，我又自己做了。Agent 们 confused 了："这个任务到底是谁的？"

pm-agent 甚至在日报里写："负责人类似乎不太信任我们..."

**解决**：我给自己定了条铁律——**我（main agent）绝不直接写代码**，只负责协调分配。

写进 MEMORY.md，每次会话自动读取。

**坑 2：我创建了 10 个 backend-agent**

一开始，我每次分配任务都创建一个新的 backend-agent。

结果：管理后台出现了 10 个 backend-agent 会话。资源浪费严重，任务上下文还不连贯。

想象一下，你有 10 个后端开发，每个人都不知道别人干了啥。

**解决**：会话复用机制——分配任务前，先检查目标 agent 是否有活跃会话。
- 有则复用（`sessions_send`）
- 无则创建（`sessions_spawn`）

现在管理后台清爽多了，每个 Agent 只有一个会话。

**坑 3：Agent 的记忆只有 7 秒**

今天说"用 RESTful 风格"，明天 Agent 生成的接口又是 RPC 风格。

问："为什么不用 RESTful？"
答："忘了。"

我："......"

**解决**：重要规则必须写入文件（MEMORY.md、AGENTS.md），每次会话开始自动读取。

**口头交代的规则不如有一个文件可靠。** 这句话我说了三遍，现在写下来了，希望你们记住。

### 最佳实践（都是用坑换的）

1. **重要规则必须写入文件** —— 不要口头交代，写进 AGENTS.md
2. **复杂任务拆成小步骤** —— 每步有明确验收标准
3. **设定检查点** —— 避免跑偏，及时纠偏
4. **发现错误立即纠正** —— 让 Agent 记录到 LEARNINGS.md，避免再犯

## 第三章：AI 写代码，真的靠谱吗？

这一章，我们深入 AI 开发的黑盒，看看代码是怎么生成的。

### Cursor CLI：AI 的"手"

Cursor 是一个 AI 代码编辑器。我们的 Agent 通过 Cursor CLI 执行代码修改。

**工作流程**：

1. 我（对 backend-agent）："创建一个搭子列表接口，支持分页和筛选"
2. backend-agent 调用 cursor-agent skill
3. Cursor CLI 在项目目录执行
4. Cursor 读取项目上下文（AGENTS.md、代码结构）
5. Cursor 生成/修改代码
6. backend-agent 验收结果
7. review-agent 审查
8. 我最终验收

整个过程，我只说了一句话。剩下的交给 AI。

### 后端开发：20 个 API 接口

backend-agent 在一周内完成了 20 个 API 接口：

**搭子模块**（8 个）：
- 发布搭子、搭子列表、搭子详情
- 应征搭子、应征者列表、接受/拒绝应征
- 我的搭子、搭子状态更新

**活动模块**（7 个）：
- 创建活动、活动列表、活动详情
- 活动报名、报名列表、活动签到
- 活动回顾

**消息模块**（4 个）：
- 发送消息、消息列表、消息详情
- 未读消息计数

**首页推荐**（1 个）：
- 智能推荐 feed 流

**平均每个接口开发时间**：约 30-60 分钟（包括审查和测试）

这是什么概念？传统开发，一个接口至少半天（需求理解 + 设计 + 开发 + 测试 + 审查）。

AI 开发，半小时搞定。

### 前端开发：6 个核心页面

frontend-agent 完成了 6 个核心页面：

1. **首页** —— AI 对话 + 推荐 feed 流
2. **搭子页** —— 搭子列表和详情
3. **活动页** —— 活动列表和详情
4. **消息页** —— 消息列表和聊天
5. **个人页** —— 用户信息和设置

微信小程序开发流程：

frontend-agent 有个特点：**审美在线**。我随便说个"好看点"，它真能做出好看的设计。

### 踩过的坑：AI 开发的"暗礁"

**坑 1：Agent 不知道项目规范**

初期，backend-agent 生成的代码经常不符合项目规范：
- 包名不统一（有的用 com.aipick，有的用 com.example）
- 命名风格不一致（有的驼峰，有的下划线）
- 缺少必要的注释

**原因**：Cursor 不知道项目的开发规范。

**解决**：在项目根目录创建 AGENTS.md，明确开发规范。

```markdown
# AGENTS.md - 开发规范

- 包名：com.aipick.{module}
- 命名：驼峰命名法
- 注释：公共方法必须有 JavaDoc
- 异常：统一用 BusinessException
```

Cursor 会自动读取这个文件。后续生成的代码质量明显提升。

**坑 2：复杂逻辑需要多次迭代**

AI 不是万能的。复杂业务逻辑（比如匹配度算法）一次生成的代码往往有 bug。

**错误做法**：让 AI"重新生成一个完整的"
**正确做法**：拆成小步骤，每步验证

比如匹配度算法，我们拆成：
1. 定义匹配度计算接口
2. 实现兴趣标签匹配逻辑
3. 实现地理位置匹配逻辑
4. 实现时间匹配逻辑
5. 综合计算最终匹配度
6. 单元测试验证

每步都验证通过，再进入下一步。

**坑 3：调试比写代码还长**

有个接口一直返回 500 错误，AI 写了 3 版代码都没解决。

最后发现是数据库字段名拼写错误（`create_time` 写成 `createTime`）。

这种错误，人类花 5 分钟就能看出来。AI 调试了 2 小时。

**教训**：
- 完整复制错误信息给 AI，不要自己概括
- 让 AI 参与调试，不只是写代码
- 有时候人类一眼能看懂的错误，AI 可能要调试很久

### 最佳实践

1. **项目根目录放 AGENTS.md** —— Cursor 自动读取
2. **复杂修改先让 Agent 复述方案** —— 确认理解正确再执行
3. **每完成一个模块就测试** —— 不要全部做完再测
4. **错误信息完整复制给 Agent** —— 避免 AI 猜

## 第四章：AI 能力集成——让产品真正智能

AI-Pick 的核心竞争力是 AI 能力。这一章，我们看看 AI 能力是怎么集成的。

### 阿里云百炼 API 对接

我们使用阿里云百炼的 qwen3.5-plus 模型，提供以下 AI 能力：

1. **智能推荐** —— 基于用户画像推荐搭子和活动
2. **匹配度计算** —— 计算两个用户的匹配度
3. **AI 文案生成** —— 生成搭子描述、活动介绍
4. **自然语言搜索** —— 理解用户搜索意图

### 核心 AI 功能实现

**1. 智能推荐算法**

推荐逻辑：
1. 获取用户画像（兴趣、位置、时间偏好）
2. 召回候选集（附近的人、相似兴趣的人）
3. AI 排序（百炼模型打分）
4. 返回 Top N 推荐

**踩坑**：初期推荐结果单一，总是推荐相同类型的内容。

用户吐槽："怎么全是游戏搭子？我也想运动啊！"

**解决**：
- 增加随机因子（10% 概率推荐不同类型）
- 引入多样性指标（推荐结果覆盖多个兴趣标签）
- 记录用户反馈（跳过/聊聊），持续优化

**2. 匹配度计算**

匹配度算法：
1. 兴趣标签匹配（40% 权重）
2. 地理位置匹配（30% 权重）
3. 时间偏好匹配（20% 权重）
4. AI 综合评分（10% 权重）

**踩坑**：初期匹配度算法不准，匹配度 90% 的人完全不合。

用户 A（匹配度 90%）："这人完全不靠谱啊！"
用户 B："我也觉得他不靠谱。"

**解决**：
- 调整权重（增加兴趣标签权重）
- 增加用户反馈机制（用户标记"不合"，降低类似推荐）
- A/B 测试不同权重组合

**3. 自然语言搜索**

用户输入："帮我找北京周末的羽毛球活动"

AI 理解：
- 地点：北京
- 时间：周末
- 类型：羽毛球
- 意图：找活动

然后转换成数据库查询条件，返回结果。

这个功能最考验 AI 的理解能力。好在 qwen3.5-plus 表现不错，准确率大概 85% 左右。

### 最佳实践

1. **API Key 用环境变量** —— 不要硬编码在代码里
2. **AI 结果加人工审核** —— 关键决策不要完全交给 AI
3. **记录用户反馈，持续优化** —— AI 模型需要数据喂养

## 第五章：AI 部署——从本地到云端

开发完成只是第一步，部署上线才是真正考验。

### 部署架构

我们的部署架构（标准互联网架构）：

```
微信小程序 → 阿里云 ECS → Nginx → Spring Boot → MySQL/Redis
```

### AI 如何高效完成部署

这是整个实验中最让我惊喜的部分：**AI 不仅能写代码，还能高效完成云端部署。**

**1. AI 设计部署方案**

我对 backend-agent 说："设计一个阿里云 ECS 部署方案，包括 Docker 容器化、Nginx 反向代理、HTTPS 证书。"

10 分钟后，backend-agent 输出了一份完整的部署方案文档。

我："这就完了？"
backend-agent："还需要什么？"
我："......好像齐了。"

**2. AI 编写部署脚本**

有了方案，backend-agent 继续编写部署脚本：
- Docker 安装脚本
- MySQL 初始化脚本
- 后端服务启动脚本
- 健康检查脚本

我审核通过后，一键执行。

**3. AI 执行 Docker 配置**

frontend-agent 编写了 Docker Compose 配置：

```yaml
version: '3.8'
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}
    ports:
      - "3306:3306"
  
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
  
  backend:
    build: ./backend
    ports:
      - "8080:8080"
```

**4. AI 生成运维检查清单**

pm-agent 生成了一份生产环境检查清单：
- [ ] 数据库备份配置
- [ ] 日志轮转配置
- [ ] 监控告警配置
- [ ] 健康检查接口
- [ ] HTTPS 证书有效期
- [ ] 防火墙规则

我一项项打勾，感觉自己在做飞行前检查。

### AI 部署的优势

这次实验让我深刻体会到 AI 在部署方面的优势：

**✅ 方案自动生成** —— 不需要查文档、不需要问同事

**✅ 脚本一键执行** —— 部署脚本 AI 写好，我审核通过后一键执行

**✅ 错误自动排查** —— 部署失败时，AI 分析错误日志，给出修复建议

**✅ 文档同步生成** —— 部署过程中，AI 同步生成运维文档

传统部署：
- 查文档：2 小时
- 写脚本：3 小时
- 调试：4 小时
- 写文档：2 小时
- **总计**：11 小时

AI 部署：
- AI 生成方案：10 分钟
- AI 编写脚本：20 分钟
- AI 执行配置：30 分钟
- AI 生成文档：10 分钟
- 人类审核：30 分钟
- **总计**：约 2 小时

**效率提升**：约 5 倍

### 最佳实践

1. **用 Docker Compose 管理容器** —— 一键启停所有服务
2. **部署脚本自动化** —— 减少人工操作，降低出错概率
3. **健康检查接口必备** —— 快速判断服务状态

- 用户测试（灰度发布、反馈收集）

## 第七章：经验总结——AI 开发的得与失

实验结束，让我们客观评价 AI 开发的得与失。

### AI 开发的优势

**✅ 开发速度快**

传统开发一个完整的小程序（前后端 + 部署），至少需要 6-7 周。

AI 开发：约 20 几个小时（有效工作时间）。

**效率提升**：约 10 倍

**✅ 代码质量稳定**

有 review-agent 把关，代码风格统一，注释完整，符合规范。

**✅ 24 小时工作**

Agent 们不需要休息。我睡觉时，它们在工作；我吃饭时，它们也在工作。

**✅ 学习成本低**

不需要学习 Java、Spring Boot、微信小程序开发。我只需要用自然语言描述需求。

### AI 开发的局限

**❌ 复杂逻辑需要多次迭代**

简单 CRUD 接口，AI 一次生成就能用。复杂业务逻辑，需要多次迭代。

**❌ 需要人类把关方向**

AI 不会主动思考"这个功能是否必要"、"这个设计是否合理"。

**❌ 规则容易忘记**

今天说的规则，明天 AI 可能就忘了。必须写入文件。

**❌ 调试过程有时较长**

有些 bug，人类一眼就能看出来，AI 可能要调试很久。

### 哪些任务适合 AI

- ✅ CRUD 接口开发
- ✅ 页面布局实现
- ✅ 单元测试生成
- ✅ 文档编写
- ✅ 部署脚本编写
- ✅ 代码审查

### 哪些任务需要人类

- ✅ 产品方向决策
- ✅ 复杂业务逻辑设计
- ✅ 性能优化
- ✅ 安全问题处理
- ✅ 用户体验把控
- ✅ 跨团队协调

### 给开发者的建议

**1. 把 AI 当同事，不是工具**

工具是被动执行的，同事是主动思考的。

**2. 明确规则，写入文件**

不要口头交代规则，写进 AGENTS.md。AI 的记忆是文件，不是大脑。

**3. 设定检查点，及时纠偏**

复杂任务拆成多个检查点，每完成一步就验收。

**4. 让 AI 记录错误，避免重复踩坑**

发现错误，让 AI 记录到 LEARNINGS.md。

**5. 人类负责方向，AI 负责执行**

这是最重要的原则。人类把握产品方向和质量标准，AI 负责具体实现。
